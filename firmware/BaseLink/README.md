# BaseLink_LQR_BT — direct EVOFOX Bluetooth + expression ring



Your original `BaseLink_LQR` folder is untouched — keep it as the known-good
fallback. This is a parallel sketch with **ESP-NOW removed** (as you approved),
which frees the 2.4 GHz radio for Bluetooth, so the EVOFOX One S now pairs
**directly to the robot**. The bridge ESP32 is no longer needed at all.

```
EVOFOX One S --BT--> robot                (driving, one hop)
Cubie --USB 'V' lines--> robot            (vision override, unchanged)
```

## What changed vs your stable firmware (the complete list)

**Untouched, byte-identical:** `imu_sensor.*`, `stepper_control.*`, the entire
LQR/LQI controller, arbitration, serial protocol, safety limits, gestures.
`vision_guard.py` works exactly as before — Radxa authority is the same.

**New files:** `bt_gamepad.h` (replaces `espnow_comm.h`, exposing the *same
four globals with the same units*, so the arbitration and enable-edge code
did not move), `led_ring.h/.cpp` (the ring).

**`BaseLink_LQR_BT.ino` diff:** include swap; `espnow_receiver_begin()` →
`btgamepad_begin()`; `btgamepad_update()` + a gesture-button switch added next
to `pollSerial()`; `leds_begin()` in setup; `leds_update(li)` block before the
odometry stream; two one-line `leds_event()` calls (arm, fall). That's all.

**`config.h`:** one appended section at the bottom (LED + pad constants).
Everything above it is your file, unchanged — including all gains.

## Why the ring can't hurt the balance loop

FastLED/Adafruit bit-banging disables interrupts ~30 µs per LED per frame —
that starves your 20 kHz stepper ISR, which is why FastLED was removed from
the old firmware. This uses **NeoPixelBus over the ESP32 RMT peripheral**:
WS2812 timing is generated by hardware, `Show()` never disables interrupts,
and the whole animation engine costs microseconds per frame at 30 fps. The
BT stack additionally runs on core 0 while your control loop owns core 1.

## Build setup (one time)

1. Arduino IDE → Preferences → Additional Board Manager URLs, add:
   `https://raw.githubusercontent.com/ricardoquesada/esp32-arduino-lib-builder/master/bluepad32_files/package_esp32_bluepad32_index.json`
2. Boards Manager → install **esp32_bluepad32** → select your DevKit under
   the "ESP32 + Bluepad32 Arduino" section (same flash/partition settings
   as before).
3. Library Manager → install **NeoPixelBus by Makuna** (≥ 2.8.0).
   TMCStepper / ISM6HG256X / QMC5883L stay as-is.
4. Flash. Boot log ends with `[PAD] Bluepad32 ready`.

## Pairing (one time)

Forget the pad from your phone first. Power the robot, then hold **Home + B**
on the One S (or **A + Home**) until the LED blinks — Bluepad32 auto-pairs
while no controller is connected. It reconnects by itself on every Home press
afterwards. If pairing ever jams: uncomment `BP32.forgetBluetoothKeys()` in
`bt_gamepad.h`, flash once, re-pair, comment it back.

## Controls

Left stick Y drive, right stick X steer. **START = arm, SELECT = disarm
(motors off → it falls, catch it).** Y = nod yes, B = nod no, X = spin,
**A = dance (party mode!)**, LB = stiff-hold toggle. If any direction is
mirrored flip `PAD_FWD_SIGN` / `PAD_STEER_SIGN`; if buttons land wrong, the
`[PAD] btn=0x.... misc=0x....` debug line tells you the real bits to put in
`bt_gamepad.h`. Pad disconnect mid-drive = inputs zero, robot holds its spot.

## Ring wiring (GPIO 15)

Ring 5V → 5 V rail (NOT the 3V3 pin), GND → common ground, DIN → **330 Ω
resistor** → GPIO 15, and ideally a 470–1000 µF cap across the ring's 5V/GND.
GPIO 15 is free in your pinmap and safe as an output; the ring's DIN is
high-impedance so it won't disturb the boot strapping. `LED_MAX_BRIGHT 70`
caps worst-case draw around ~0.3 A — 16 LEDs at full white would pull ~1 A,
so raise it only if your 5 V rail has headroom. Set `LED_FRONT_INDEX` to
whichever LED faces forward and `LED_DIR_CW` to match your mounting.

## What the ring does (priority order)

Boot: rainbow swirl while sensors settle. Fall: red "ouch" flash that fades.
Arm: green wake-up sweep. Any gesture: spinning rainbow party. **Cubie vision
override while still rolling: urgent red hazard pulse** (you'll see exactly
when the guard grabs authority). **Pushed off its spot: pink blush on both
cheeks with averted-eyes wiggle, fading as the LQI walks it back** — your shy
bounce, powered by the position error that already exists. Driving: a
cyan-white beam pointing where it's going, wider and brighter with speed,
leaning into turns, amber when reversing. Stiff hold: determined amber
breathing. Idle balancing: calm cyan breathing with a rare twinkle, warming
toward orange as tilt effort grows. Armed but lying down: green "lift me up"
pulse at the front. Asleep: a slow wandering ember with an occasional sleepy
double-blink. Pad connects: quick green wink.

## Bring-up (wheels off the ground)

1. Flash, pair, press START — arm sweep plays, wheels respond to sticks,
   beam follows your stick direction. Verify signs.
2. `L` debug still works over USB; confirm loop timing feels normal (the
   D-stream cadence should be rock steady — that's your proof BT+RMT cost
   nothing).
3. Run the vision guard drill: fire an override while driving — wheels stop
   AND the ring goes red-hazard. Two confirmations in one test.
4. Floor test at walking pace. Push it gently: blush. Press A: dance party.
