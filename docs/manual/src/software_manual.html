1About this manual

This manual is for anyone who reads, modifies or extends the 2PyBot software. It explains what each part does and why, where the code lives, and the rules that keep changes safe on a machine that moves by itself.

It describes the repository at firmware BaseLink 4.7.8 and host software 4.7.8, branch feature/lidar-autonomy. File paths are relative to the repository root. Day-to-day operation is covered in the user manual (UM-2PB-001); hardware in the hardware manual (HW-2PB-004).

1.1 Ground rules

  • The controller owns motion. Everything that can move a wheel runs on the ESP32. The host may stop the robot but can never arm it.
  • Fail safe, not fail silent. Every link has a timeout; losing a signal stops or holds the robot rather than continuing on stale data.
  • Measure, then change. Control changes are driven by recordings (section 13), not by feel alone.
  • Physical tests are operator initiated. No build, script or deployment arms or drives the robot.

4Controller firmware

4.1 Toolchain and build

The firmware builds with Arduino CLI against a locked toolchain (scripts/firmware/toolchain.json): the Bluepad32 ESP32 core 4.1.0 (ESP-IDF 4.4.5) and fixed library versions (ISM6HG256X, QMC5883L, NeoPixelBus). The board uses the Huge APP partition scheme (3 MB application at 0x10000).

python scripts/firmware/build.py --output-dir build/BaseLink --require-toolchain-lock

The build writes the application image, bootloader, partition table and a manifest.json with version, SHA-256, source commit and a source fingerprint. The firmware version string must equal VERSION; scripts/versioning.py --check enforces it.

4.2 The main loop

loop() in BaseLink.ino runs at a fixed 200 Hz (5 ms). Every cycle performs, in order:

  1. Heartbeat for the stall guard.
  2. Sensors: IMU update and pitch filter, terrain estimate, hub motor feedback, position and speed estimates.
  3. Inputs: serial commands from the host, gamepad (Bluepad32), gestures, torch and camera stick.
  4. Drive arbitration: navigation lease, latched manual priority, host V input, gamepad, then gesture playback and the optional ToF guard.
  5. State machine: IDLE, BALANCING or SELF_RIGHTING; arming, fall and fault checks; runController().
  6. Motor transmit: one frame to each hub motor immediately after the control calculation.
  7. Housekeeping: status LED, incremental parameter dump, LED ring frame.
  8. Telemetry: O and D at 50 Hz, NR, HM and BB at 10 Hz, SR at 20 Hz, optional HV at 100 Hz.

4.4 Balance controller

The balance law is a full-state LQR with integral action (LQI) on the linearised wheeled inverted pendulum. The output is a wheel acceleration command u:

hold:    u = -(K1·e_x + K2·v + K3·θ + K4·ω + K5·∫e_x)
driving: u = -(K2·clamp(v - v_ref, ±VERRMAX) + K3·θ + K4·ω)
  • States: position error e_x (clamped to EXCLAMP), wheel speed v, body pitch θ, pitch rate ω and the integral of position error.
  • Default gains: K1 −7.32, K2 −7.45, K3 −42.95, K4 −6.69, K5 −2.11.
  • Driving: the position terms are dropped and the speed error is clamped by VERRMAX (0.7 m/s), so a stick release brakes at once but the velocity term can take at most about 5 m/s². The hold point is dragged along at BRAKELK × speed ahead.
  • Hold: when the reference is inside the deadband and the speed below 0.05 m/s, the full LQI vector holds the current point. Stiff hold uses the separate gain set S1 to S5.
  • Climb: a separate gain set C1 to C5 with its own position reference and integral, blended in and out over 0.75 s.
  • Saturation: u is clamped to ±6 m/s². When speed or current saturates, the hold point bleeds toward the robot and the integral decays, so attitude regains authority (balance before position).
  • Speed estimate: with VELSRC = 1 the controller uses each wheel's sample-timed velocity from hub_drive, filtered at 15 Hz.

The acceleration is integrated into a wheel speed command for the inner loop in hub_control.h, which converts it to motor current: mass feed-forward plus a velocity PI in the common channel, a separate PI for steering, and balance-first allocation of the current limit.

4.5 Hub motor link

Each M0601 has its own RS485 bus at 115200 baud. Every 5 ms cycle sends exactly one 10-byte frame to each motor and never waits for the previous reply.

FrameBytes
Drive (0x64)id, 0x64, current high, current low, 0, 0, accel, brake, 0, CRC8. Current ±32767 = ±8 A.
Query (0x74)id, 0x74, 0 × 7, CRC8. Reply carries temperature.
Mode (0xA0)id, 0xA0, 0 × 7, mode byte (vendor format, no CRC).
Replyid, mode, current, rpm, position (drive) or temperature (query), fault, CRC8.
  • CRC: CRC-8 (polynomial 0x8C reflected). Because an 8-bit CRC passes about one corrupt window in 256, replies that are impossible are rejected as well: fault bits outside 0x1F or more than 900 rpm.
  • Confirmation: a fault must repeat in three consecutive replies (about 15 ms) and a mode change in two before they count. Ignored faults are logged.
  • Velocity: the 16-bit position in every drive reply is unwrapped and differentiated against the request send time, then filtered at 30 Hz.
  • Health: a wheel is healthy with a fresh reply, current mode, valid position and no confirmed fault. Otherwise the controller disarms and keeps sending zero current.

4.6 Safety layers

LayerBehaviour
Zero from power-onThe first lines of setup() start both RS485 ports and send zero-current frames, and keep doing so during the host wait. The M0601 holds its last setpoint otherwise.
Stall guardAn esp_timer task checks the loop heartbeat every 20 ms: zero current after 150 ms of stall, restart after 800 ms (5 s while a blocking maintenance command runs with motors off).
Fall and rateDisarm beyond MAXTILT (55°) or MAXRATE (450°/s).
Motor healthDisarm on link loss, wrong mode or a confirmed fault (section 4.5).
Loop overrunDisarm if a cycle takes longer than 20 ms.
Safety bubbleBG distances become speed limits every cycle for every drive source; fail closed after BUBSTALE (300 ms).
Navigation leaseAutonomy only through a granted lease; 500 ms timeout; any stick movement takes over.
ArmingOnly local START or serial E on USB; never a network command or the lease.
Reset reasonPrinted at every boot and kept in the host's persistent controller log.

Bubble guard in detail

On each BG line the guard stores the distances corrected for the scan age and the current position. Every cycle it subtracts the distance travelled since then and limits the drive reference to the braking speed:

v_max = sqrt((a·t)² + 2·a·(d - m)) - a·t      a = BUBDEC, t = BUBLAT, m = BUBMRG

A commanded turn is zeroed if the turn flags block that direction. The limit applies after the drive arbitration, the ToF guard and inside climb mode.

4.7 Parameters and storage

Every tunable is declared once in PARAM_TABLE (params.h) with key, default, minimum, maximum, group and description. The same table generates the RAM struct, bounds checks, the protocol dump and storage. Values with equal minimum and maximum are fixed.

  • Storage: all values are saved as one NVS blob of (FNV-1a key hash, value) records. A save clears the namespace, writes the blob and markers, reopens read-only and compares byte for byte before replying PS!,saved.
  • Migrations: one-time markers (_cur5s, _input3, _brake2) let a new firmware replace specific saved values with new defaults. The firmware worker honours matching capability flags (for example PR,BRAKEPROFILE,2).
  • Diagnostics: PN lists NVS usage per namespace; PX,ns erases an obsolete namespace (never Bluetooth, PHY or Wi-Fi).

4.8 LED ring engine

led_ring.cpp renders at LEDFPS through I2S DMA and skips a frame rather than wait. One state wins each frame, in priority order: test pattern, fatal, start-up loader, fall, error code, self-uprighting, gesture, pushed, armed animations, ready heartbeat. Angles are converted to LED indices with LEDFRONT and LEDDIR.

4.9 Start-up sequence

  1. Zero the motors, print the reset reason, load parameters, start the loader animation.
  2. Wait for the host acknowledgement BR,1 (the host sends it when its camera and hotspot are up). Motors stay at zero.
  3. Initialise the IMU and motors, settle for 3 s, calibrate the gyro.
  4. Start the gamepad and payload, report BS,READY, arm the stall guard. The robot waits for START.

6.2 Process structure

console/server.py creates a FastAPI app on port 8080 and starts these concurrent tasks: link.run() (serial reader), camera supervisor, ToF acquisition and publisher, calibration, object detection, firmware monitor, autonomy loop (20 Hz), host readiness publisher, camera restore and the bubble publisher. The SLAM engine and the lidar driver run in their own threads. The system map and Maps pages are mounted as sub-applications at /sysmap and /slam.

6.3 Serial link

serial_link.py is the only code that touches the controller port. It opens it exclusively without resetting the ESP32, parses every record into tel, debug, hub, nav, bubble and the parameter table, publishes to WebSocket subscribers, and feeds raw O/D lines to line listeners (SLAM).

  • Controller log: every log line goes to /var/lib/2pybot/logs/controller.log (5 × 4 MB rotation), including telemetry LOST and restored edges. Boot ROM noise is stripped.
  • Recorder: record_start(seconds) writes every raw line with a host timestamp for analysis.
  • Port discovery: if /dev/ttyUSB0 disappears, it also tries /dev/2pybot, serial by-id links and other ttyUSB devices.
  • Parameter operations: serialised; a write waits for the controller acknowledgement; a save waits for the verified reply and re-reads the table.

6.6 Safety bubble on the host

For every usable scan, slam/bubble.py removes points on the body (footprint from the lidar centre: front 7, back 8, right 11, left 18 cm including 1 cm growth), rejects isolated points without a neighbour within 6 cm or a match in the previous scan, and computes the free distance inside the corridor swept along the current arc (curvature from measured speed and yaw rate). It also tests rotations of ±0.12 to 0.60 rad for turn clearance and the free travel for 24 headings. bubble_guard.py sends the result as BG on every new scan.

6.7 Autonomy

autonomy.py owns the lease and supervision; missions.py contains the planners.

  • Lease: AN with a random token; granted only while balancing with the gamepad connected and sticks centred. AU commands at 20 Hz with an increasing sequence.
  • Supervision: the page sends a heartbeat at least every 3 s; feedback older than 0.35 s, a takeover, a lost balance or a hidden page pauses or stops the mission.
  • Roam: reactive states cruise, choose, turn and back up, using the bubble's free travel per heading and a visited-cell map.
  • Go to: A* on a 10 cm cost map (robot radius 17 cm, extra cost within 45 cm of walls, unknown space blocked), line-of-sight smoothing, pure pursuit on the SLAM pose, re-planning around new lidar obstacles after 2 s blocked.
  • Explore: repeated Go to toward the nearest reachable frontier until none remain.
  • Teach and replay: records commanded speed and turn rate and replays them on the original timing.

6.8 Camera, depth sensor, system map

  • Camera: native/2pybot_hwstream captures NV12 from the IMX708, encodes H.264 on the Cedar engine and publishes to MediaMTX; stream.py supervises it. A JPEG snapshot is written once per second. Lens calibration lives in calibration*.py.
  • Depth sensor: tof_worker.py runs ST's driver in a separate process through ctypes so a driver hang cannot block the console; tof.py builds the corridor guard.
  • System map: sysmap_health.py judges every block from its own evidence and suppresses alarms downstream of a failed link.

6.9 Power-down mode

power.py switches off what heats the robot while it is unused. Asleep, the camera pipeline is paused (the stream supervisor does not restart it), the lidar driver is stopped and its motor speed set to zero, the depth worker is stopped (it stops ranging on exit) and not restarted, object detection and autonomy are switched off, and the controller is sent SL,1. A 1 Hz task re-sends the wanted state after a controller reset. Host readiness ignores the camera while asleep, so a controller restart still passes its start-up gate. The Radxa does not suspend: Wi-Fi would go down and the board has no wake-on-LAN, so the console must stay up to wake the robot. The state is not persisted, so deployments and their health checks always start awake.

Gamepad re-pair

Bluepad32 4.1 keeps pairing state in two NVS namespaces: BTstack (link keys, BLE bonds, BLE root keys) and bp32 (its settings). Deleting keys through the library at runtime left its BLE state inconsistent with the EVOFOX pad. BT,FORGET therefore erases both namespaces directly and restarts, so BTstack and Bluepad32 reload from empty storage. This is the Bluetooth part of a full flash erase, without touching parameters or calibration.

6.10 Firmware worker

The worker flashes with esptool through its own process. It snapshots live tuning, backs up the boot and NVS region, verifies the installed image as a rollback copy, writes only the application at 0x10000, verifies it, confirms boot and NVS are unchanged, boots the controller and restores tuning. Any failure writes back the previous image. Host-side state such as the camera profile is checked but can only add a warning.

10.3 Deploying a branch

git fetch origin BRANCH && git show FETCH_HEAD:scripts/radxa/deploy_branch.py | sudo python3 - BRANCH
  1. deploy_branch.py checks the robot is stopped and idle, fast-forwards the checkout, writes the request and starts the deploy unit.
  2. deploy.py plans what changed, downloads and verifies the bundle, stages an immutable release from git archive, prepares the environment, takes the maintenance lock, switches the release, restarts services and flashes the firmware through the worker.
  3. It waits for the controller to report READY, records the result and, if the app changed, starts a background unit that downloads and publishes the APK.

12Extending the system

12.1 Add a controller parameter

  1. Add an X(field, "KEY", default, min, max, "GROUP", "description") row to PARAM_TABLE.
  2. Read it as P.field in the code. It appears in the console, app and TUI automatically.
  3. If an existing saved value must be replaced, add a migration marker (section 4.7).

12.2 Add a serial command

  1. Parse it in handleLine() before the generic handlers, refuse it in unsafe states, reply or log.
  2. Advertise support with a new PR capability row in params.cpp.
  3. Document it in PROTOCOL.md and this manual.

12.3 Add an API endpoint and a TUI action

  1. Add the route in server.py; check controller connection, armed state and capability; send through link.send().
  2. Add a CLI subcommand in bot_cli.py and, if useful, an action on a TUI page in bot_tui.py.

12.4 Add an LED state

Add an input to LedInputs, fill it in the loop, and draw it in leds_update() at the right priority. Keep red for errors and keep every other LED off during direction animations.

12.5 Add an autonomy mission

Write a planner class in missions.py with step(now, dt, pose, bubble, depth_cap, measured_v) returning a Step, register its kind in Autonomy.start_task(), and add it to the step 8 card. Never send motion from the planner directly: Autonomy applies the bubble and owns the lease.
