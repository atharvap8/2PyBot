Part 1 · Hardware

Compute, actuation, sensing, power and mechanics.

Architecture and compute

H1Why are there two computers, an ESP32 and a Radxa?

They have different timing requirements. Balancing needs a deterministic 200 Hz loop with bounded latency from IMU sample to motor command. A Linux board cannot guarantee that while it also encodes video and runs SLAM. The ESP32 therefore owns every actuator and the gamepad; the Radxa owns perception, the user interface and updates.

The split also defines the failure behaviour. If the Radxa crashes, Wi-Fi drops or the console restarts, the robot keeps balancing and the operator keeps the gamepad stop. The host can stop the robot but can never arm it.

H2How are the two boards connected and synchronised?

Over USB serial at 460800 baud with line-based ASCII records. The ESP32 sends odometry and IMU data at 50 Hz, controller state at 50 Hz and motor feedback at 10 Hz. The host sends drive input, parameter commands and stop requests.

Clocks are not shared. Host consumers map the ESP32 millisecond counter onto host time using the minimum observed offset over a sliding window, which removes USB and scheduling delay because transport only ever adds latency.

H3What prevents the ESP32 from starting before the host is ready?

A boot gate on the host holds the ESP32 in reset through the USB adapter's RTS line until the host services are up. After release, the firmware waits for an explicit BR,1 acknowledgement before it calibrates the IMU and starts the motors' communication. Arming stays closed until that sequence completes, so a USB reset during deployment cannot produce a powered, uncalibrated controller.

H4Why the Radxa Cubie A7A?

It provides a MIPI CSI camera input with a hardware H.264 encoder, enough CPU for numpy-based SLAM, onboard Wi-Fi for a hotspot plus a client connection, and free UART and I2C on the 40-pin header for the lidar and depth sensor. The hardware encoder keeps camera streaming at a few percent of CPU, which leaves headroom for mapping.

Motors and power

H5Why BLDC hub motors in current mode instead of steppers or velocity mode?

An inverted pendulum is controlled through wheel torque, because torque produces the acceleration that rotates the body back. Current mode gives the controller direct torque authority (torque ≈ Kt × current, Kt = 0.75 N·m/A) with no inner velocity loop inside the driver that would add lag or fight the balance loop.

Velocity mode was evaluated and removed: the drivers' internal speed loop and position-derived feedback delay produced oscillation under load. Steppers were used in earlier revisions and replaced because they lose steps under shock loads and cannot report torque.

H6How is the RS485 link scheduled, and what happens if a reply is lost?

Each motor has its own RS485 bus. Every 5 ms control cycle sends exactly one frame to each motor, regardless of whether the previous reply arrived. A missed reply costs one feedback sample, not a torque update. Earlier revisions waited for replies and froze a wheel's torque for up to 25 ms after a single late frame.

Every reply carries the motor's actual mode byte and fault byte. If a motor reports the wrong mode, a fault, or no reply for 60 ms, the controller disarms.

The frame check is an 8-bit CRC, so on a noisy link a misaligned 10-byte window passes it about once in 256 tries. Replies that pass the CRC but are impossible (fault bits outside the documented 0x1F, more than 900 rpm) are rejected and the parser resynchronises. A fault must repeat in three consecutive replies (about 15 ms) and a mode change in two before they count. This removed false "overheat" trips caused by a single corrupt frame; ignored frames are logged.

H7How is wheel speed measured?

From the unwrapped 16-bit absolute position in every drive reply, differentiated against the time the request was sent (when the driver sampled the position) and low-pass filtered at 30 Hz. Using the reply arrival time instead adds UART and loop jitter that, multiplied by wheel speed, becomes velocity noise at high speed. Since 4.7.5 the balance controller also takes its speed from these per-wheel estimates (setting VELSRC); before, it differenced the averaged position every loop, which aliased reply jitter into noise that grew from 0.02 to 0.07 m/s rms with speed and drove a 22 Hz oscillation in climb mode. The motors' reported RPM is coarse and delayed, so it is kept only as a fallback source selectable with HUBVSRC. Positions are converted to 4096 counts per revolution and per-wheel forward signs before any control code sees them.

H8What limits the motor current, and why 2.7 A?

A per-motor software limit (CURRENT, default 2700 mA, maximum 4400 mA) is applied before the command is quantised to the driver's ±8 A scale. 2.7 A gives about 2 N·m per wheel, which recovers the 2.6 kg robot from the tilts it meets in normal driving while staying well inside the drivers' thermal and overcurrent limits on a 5S supply.

Balance current is allocated first; steering only receives the remaining headroom per wheel. A sharp turn therefore cannot steal the torque needed to catch a fall.

H9Does the robot measure battery voltage?

No. The 18 V supply value is configuration only and is used for the informational no-load speed estimate. It is not used to scale commands, and there is no hidden voltage-based speed derating.

Sensors

H10Which IMU is used and how is pitch computed?

An ST ISM6HG256X accelerometer and gyroscope at 960 Hz, ±4 g and ±2000 dps. Gyro bias is calibrated at rest on every start. A six-axis Mahony filter fuses gyro and accelerometer; its accelerometer trust drops automatically when the acceleration magnitude departs from 1 g by more than 0.2 g, so driving acceleration does not tilt the estimate. A second-order 50 Hz filter smooths pitch, and the pitch rate comes directly from the calibrated gyro axis.

H11What does the lidar contribute, and what are its limits?

The Slamtec RPLIDAR C1M1R2 gives a 360° range scan at 20 Hz in a horizontal plane 265 mm above the floor. It is the primary localization sensor. Its limits are geometric: it sees a single slice, so objects lower than 265 mm or overhangs above it are invisible to it, and any forward body lean tilts the slice towards the floor.

The C1 needs 460800 baud. The A733 UARTs normally run from a 24 MHz clock, which cannot divide to that rate, so a device-tree overlay moves them to a 96 MHz clock. The motor speed command is accepted only after scanning has started, which is how the 20 Hz rate is applied.

H12Why add a VL53L5CX if there is a lidar?

It covers what the lidar plane misses. The VL53L5CX returns an 8×8 grid of distances over a 45° field of view at 10 Hz, from 210 mm height, 40 mm left of centre. Its points are projected into 3D: returns 4 cm to 50 cm above the floor are low obstacles; returns more than 6 cm below the floor indicate a drop-off. Its down-tilt is estimated from floor returns in the lower rows while the robot balances.

It is too narrow for scan matching, so it feeds a separate map layer and the optional forward speed guard, not localization.

H13Is the compass used for heading?

No. Hub motors and steel structure make the magnetometer unreliable indoors. Heading comes from wheel odometry and the gyro vertical axis, corrected by lidar scan matching. The compass value is reported for diagnostics only.

H14How is the camera streamed with low latency?

The IMX708 frames go through the Allwinner ISP into the hardware H.264 encoder and are published by MediaMTX. Clients receive them over WebRTC using WHEP on port 8889, which avoids the multi-second buffering of HLS. The pipeline reports capture-to-publish time, typically around 33 ms.

Mechanics and safety

H15Why is the lidar offset from the centreline, and does it matter?

It is placed 31 mm right of centre on the axle line for packaging. The offset is part of the sensor transform, so every scan point is expressed in the robot frame before matching. Placing it on the axle line keeps it from translating when the body pitches.

H16What happens when the robot falls?

Beyond 55° tilt or 450°/s pitch rate the controller commands zero torque and disarms; brakes are never applied, so the motors coast. The robot comes to rest on its front bumper at about 60°. The ring flashes red once and then glows red on the side that hit the ground for 10 s. From the bumper rest a local START can trigger the self-uprighting routine.

H19What happens if the controller hangs or resets?

The M0601 drivers keep applying their last current while no frames arrive, so a stalled controller could leave a wheel spinning. An esp_timer task independent of the control loop watches a loop heartbeat: after 150 ms without it, it sends zero-current frames to both motors every 20 ms; after 800 ms it restarts the ESP32 (5 s if a blocking maintenance command is running with motors off). Zero-current frames are also sent from the first milliseconds after any reset and throughout the wait for the host. The reset reason is printed at boot and kept in the persistent controller log on the Radxa.

H17Which pins needed special care on the ESP32?

GPIO0 (zoom servo) and GPIO2 (torch) are boot strapping pins. They are reset to plain GPIO and driven low before the PWM peripheral takes them, and GPIO0 has a pull-down so the chip boots normally. The status LED uses its own PWM channel and timer so its animation continues during blocking calibration.

H18Why do the camera servos detach?

Holding position draws current and makes hobby servos buzz and heat. Each servo detaches its PWM output 2 s after its own last command and drives the pin low. Both axes use the same rule, so one cannot be kept powered by movement of the other.

Part 2 · Software

Control, firmware, host services, SLAM, deployment and applications.

Balance control

S1What control law balances the robot?

A full-state LQR with integral action (LQI) on the linearised wheeled inverted pendulum. The state is wheel position error, wheel velocity, body pitch, pitch rate and the integral of position error. The output is a wheel acceleration command:

u = −(K1·e_x + K2·v + K3·θ + K4·ω + K5·∫e_x)

Default gains are K1 −7.32, K2 −7.45, K3 −42.95, K4 −6.69 and K5 −2.11. The acceleration is integrated into a wheel velocity reference for the inner current loop.

S2How does driving differ from holding position?

With the stick centred, the full LQI vector holds a position reference. When the operator drives, the position and integral terms are removed and the controller tracks the commanded velocity with K2 to K4. The hold point is dragged ahead by a braking lookahead of 0.3 s, so releasing the stick stops the robot smoothly where it naturally comes to rest. Position error fed to the LQR is clamped to 0.15 m so a large displacement causes a gentle walk back.

S3How is the acceleration command turned into motor current?

An inner loop runs per control cycle in common and differential coordinates. The common channel combines mass feed-forward (current = mass × radius × acceleration ÷ 2Kt) with a velocity PI correction. The differential channel tracks the steering target with its own PI. Common current is clamped first; differential current only uses the headroom left on each wheel.

During a recovery, when the velocity correction would oppose the balance acceleration, the correction is dropped so the loop cannot brake against a catch.

S4What happens when the actuators saturate?

Balance takes priority over position. When the velocity reference or current saturates, the hold point bleeds towards the robot and the position integral decays, so the tilt terms regain authority. The robot parks a little away from its original spot instead of falling. Integrators use conditional anti-windup throughout.

S5How does steering and heading hold work?

Steering is direct: the stick maps linearly to a wheel speed difference with a fixed authority of 4000 counts/s, without slew limiting. On release the controller first brakes the turn to zero, then latches the final heading and holds it with a PD on the encoder difference.

The differential current integral is cleared during heading hold and on every reversal of turn direction. An older design that kept integrating there stored an opposing torque that pulled the robot back after a turn, felt as spring-back.

S6How does self-uprighting work?

It is a separate controller state, entered only by a local START from the front-bumper rest (control pitch 60° ± 10°). After a 200 ms zero-torque check that the robot is resting, it applies equal forward current on both wheels from an attitude PD, I = clamp(SRKP·θ + SRKD·ω), slew-limited at 30 A/s and capped at 2.7 A. A negative pitch rate during the rise reduces or reverses the current, so the same law lifts and then catches.

Near vertical it hands over to the balance controller, seeding the velocity reference with the measured wheel speed to avoid a step. Timeouts, travel, speed, angle, rate and progress checks end a failed attempt with zero torque.

Firmware structure

S7How is the 200 Hz loop kept deterministic?

The loop runs on a fixed 5 ms period on core 1; the Bluetooth stack runs on core 0. A separate stall guard (H19) zeroes the motors and restarts the controller if the loop stops. Each cycle reads the IMU, services the motor UARTs, runs the controller and transmits both motor frames immediately after. Serial parsing has a per-cycle byte budget, and the parameter dump writes one line per cycle only if it fits the transmit buffer. A loop interval above 20 ms disarms the robot, and the worst interval is reported in telemetry.

S8How are parameters stored and protected?

All tunables are defined once in an X-macro table with key, default, bounds, group and description. The same table generates the RAM structure, bounds checks, the protocol dump and NVS storage. Every write is bounds-checked; mode, direction and radius changes are refused while motors are active.

All values are stored as one NVS blob of (key hash, value) records. An earlier layout used one NVS entry per key; about 150 entries plus the Bluetooth bonds filled the 20 KB partition, so saves failed and every boot used defaults. A save now clears the old entries, writes the blob, reopens read-only and compares it byte for byte before it reports success; PN reports partition usage. Values that must never drift, such as TRIM and MAXSTR, have equal minimum and maximum and are re-imposed on every recompute.

S9How does the gamepad connect, and why not through Wi-Fi?

The EVOFOX gamepad pairs directly with the ESP32 through Bluepad32. Driving and stopping then work without the host and without Wi-Fi, with a single radio hop and no network queuing. A stale gamepad (200 ms) zeroes its inputs while balance continues. Button actions are edge-detected so a button held during connection cannot arm the robot.

Host software

S10What runs on the Radxa?

A Python FastAPI console started by systemd. It owns the ESP32 serial port and serves the web pages, the REST and WebSocket API and the Android application endpoints on port 8080. Separate tasks run the camera supervisor, the ToF worker, the lidar driver and SLAM, the system map and the firmware update monitor. A separate firmware worker service performs flashing so the API stays responsive.

S11Why does the VL53L5CX run in its own process?

The sensor driver is ST's ultra-lite C driver loaded through ctypes, and it uploads about 84 kB of firmware to the sensor at start. Running it in an isolated process keeps a driver hang or I2C fault from blocking the console. The worker retries the first transfer, reports plain-language hints and backs off while the sensor is absent instead of polling the bus every few seconds.

S12How are parameter changes confirmed end to end?

The host serialises parameter operations. A write waits for the controller's matching acknowledgement with the applied value. A save waits for preceding writes, requires the controller's verified save reply, then re-reads the full parameter table. The API returns success only after that, and the application shows success only when the API confirms it.

S13How does the system map find the root cause of a fault?

Every block is evaluated from its own evidence: freshness, fault bytes, rates and errors. A second pass marks every block observed through a failed parent as blocked rather than failed. If the USB serial link drops, only the serial link turns red; the IMU, motors and gamepad behind it are greyed out as unknown.

Mapping and localization

S14Which SLAM approach is used, and why not ROS?

A compact 2D SLAM in numpy inside the console: a 5 cm log-odds occupancy grid and a correlative scan matcher on a blurred likelihood field, searched coarse to fine. It runs comfortably at 20 Hz on the A733, starts with the console and has no ROS installation, launch files or middleware to maintain on the robot.

S15How are wheels, gyro and lidar fused?

An extended Kalman filter tracks x, y and yaw with a covariance. Wheel distance and gyro yaw predict motion between scans, with noise that grows with distance, rotation and detected slip. Each scan match provides a pose with a covariance estimated from the shape of the matcher's score surface. A match corrects the filter only if its score passes a threshold and it passes a 99 % Mahalanobis gate against the prediction. Otherwise the scan is carried by odometry alone.

S16How is wheel slip detected?

The gyro measures true body yaw rate; the wheels report what yaw rate they would produce. Their difference, scaled by the measured scrub ratio of the chassis, is integrated between scans and inflates the process noise of the next prediction. Slip therefore lowers trust in odometry exactly when it happens.

S17How does the robot avoid mapping the floor when it leans?

A forward pitch θ lowers a beam at azimuth φ by atan(tan θ · cos φ). Forward beams dip, side beams stay level and rearward beams rise. Each beam is cut at the distance where it would reach the floor from 265 mm height, with a margin for pitch variation during the sweep. Whole scans are rejected only above 12° lean or 60°/s pitch rate. The previous design cut every beam to the forward worst case and skipped entire scans above 3°.

S18What is scan de-skew and why is it needed?

One sweep takes 50 ms at 20 Hz. While turning at 90°/s the robot rotates 4.5° during that time, which smears straight walls. Each point's capture time is interpolated across the sweep, its robot pose is taken from odometry, and the point is moved into the robot frame at mid-sweep before matching.

S19How does the robot find itself on a saved map?

On load, and automatically after about 2 s of failed matching, it runs a global search: candidate positions on a 0.25 m lattice over confidently free cells at 36 headings are scored with a subset of scan points in bounded batches, and the best eight are refined locally. The searches are serialised so the button and the automatic retry never run at the same time.

Safety bubble, autonomy and indicators

S25What is the safety bubble, and why is braking computed in the controller?

On every 20 Hz scan the Radxa finds the free distance ahead of and behind the body inside the corridor the body sweeps along the current path (straight, or an arc from the measured speed and yaw rate). The footprint is the measured body (lidar-relative front 6, back 7, right 10, left 17 cm) plus 1 cm. Returns on the body are ignored; a return counts only if a neighbour lies within 6 cm or it was also seen in the previous scan. Turning flags block a rotation that would swing a corner into a return.

The host sends distances, not speeds: BG,en,front,back,flags,age_ms. Every 5 ms the controller subtracts the wheel travel since the scan and limits the drive reference to v = √((a·t)² + 2a(d − m)) − a·t, with braking a = BUBDEC, delay t = BUBLAT and margin m = BUBMRG. An earlier version sent speed caps at 10 Hz; a cap computed 100 to 200 ms earlier was too late for a fast approach. The limit applies to every drive source and fails closed after BUBSTALE without data.

S26How do autonomy missions work, and how are they supervised?

Missions run on the Radxa and drive through the firmware navigation lease: AN requests a lease (granted only while balancing with the gamepad connected and the sticks centred), AU streams speed and yaw-rate commands at 20 Hz, and the lease expires after 500 ms without them. Any stick movement cancels it. Go to plans with A* over the inflated occupancy grid (10 cm cells, robot radius 17 cm, extra cost near walls) and follows the path with pure pursuit on the SLAM pose; it re-plans around obstacles the lidar sees when blocked for 2 s. Roam is a reactive vacuum-style planner; Explore drives to frontier cells while mapping. The supervising page must send a heartbeat at least every 3 s and pauses the mission when hidden.

S27How does the Drive view place lidar distances in the camera image?

In the browser. Each lidar return is a point in the robot frame at the 265 mm scan height; it is transformed into the camera frame using the camera mount (position, tilt, pan, roll, plus the robot's measured lean) and projected with the calibrated intrinsics, including the fisheye distortion model when the lens calibration is present. Floor features such as the bubble zone, distance rings and the planned path are projected at floor height. The mount can be adjusted live in the Align panel.

S28How are the LED ring states chosen?

The ring follows a fixed priority: test patterns, fatal error, start-up loader (until the host sends BR,1 and calibration completes), fall, numbered error codes, self-uprighting, gestures, pushed, then the armed motion animations and the ready heartbeat. Red is reserved for errors. Error n lights n LEDs clockwise from the front LED (LEDFRONT, numbered in the LEDDIR direction), which is set once with the LT test patterns. Animations are rate-limited and skip a frame rather than stall the control loop.

S29How does the robot stop when the stick is released, and why did 4.7.6 change it?

While driving, the controller tracks the stick speed with the velocity, pitch and pitch-rate terms and drags its hold point along at BRAKELK (0.3 s) ahead. On release the speed target drops to zero, the robot leans back and brakes, and position hold takes over once it is nearly still.

A recorded fall showed the limit of that scheme: reversing at 1.17 m/s, the velocity term alone asked for 8.7 m/s², the acceleration command and the 2.7 A current limit saturated for 0.6 s, and the attitude terms lost their authority. Version 4.7.5 rate-limited the speed target, which prevented the saturation but made every stop coast about 0.35 m. Version 4.7.6 removes that ramp and instead clamps the speed error to VERRMAX (0.7 m/s): braking starts at once and is strong, but the velocity term can take at most about 5 m/s², leaving headroom for balance.

S30Why did deployments become faster?

The commit bundle used to carry the Android APK (37 MB) next to a firmware image of under 1 MB, and the robot downloads GitHub release files at a few tens of kB/s. The APK is now a separate release asset: a deployment downloads only the 0.5 MB bundle, and a transient systemd unit publishes the app afterwards, outside the deployment lock, so a slow link never delays or blocks the next update.

S31How is a gamepad re-paired?

The controller accepts BT,FORGET only while disarmed. It disconnects the current pad, erases every Bluetooth bond with Bluepad32 and keeps accepting new connections. The console exposes it as POST /api/gamepad/repair, the terminal as 2pybot gamepad repair, which then waits up to a minute for the pad to connect.

Deployment, applications and quality

S20How is software deployed to the robot?

Each push builds a commit-bound bundle in CI containing the controller firmware compiled with a locked toolchain and the Android application. On the robot, a managed pull fetches the configured branch and the deployment service downloads the bundle for that exact commit. It stages an immutable host release, takes the controller maintenance lock and flashes the firmware through the worker. It then verifies that the controller reconnects READY and records the result.

S21What protects the controller during a firmware update?

The worker backs up the boot and NVS region and verifies the installed image as a rollback copy. It writes only the application partition at 0x10000 and verifies the written image. It then reads the boot and NVS region again and requires it to be byte-identical. Live tuning is captured before and restored after, with keys the new firmware does not know set aside rather than causing a failure. Any error writes back the previous image. Arming stays locked for the whole operation.

S22How is the Android application built and kept responsive?

It is a Kotlin Jetpack Compose application built in CI and signed with a stable key so updates install over previous versions. Telemetry arrives over one WebSocket. High-rate values are collected only by the composables that display them, so the navigation shell does not recompose at the telemetry rate. The 3D drive view renders on demand: after new data or a touch, then idles. Only the selected workspace is composed, so video, OpenGL and web views never run together.

S23How is behaviour verified without risking the robot?

Every change is compiled for the exact board and partition layout, and the Python host code is checked for the robot's Python version. Unit and simulation tests exist for the control and protocol logic and run when explicitly enabled in CI. Physical motion tests are always operator-initiated: no build or deployment arms or drives the robot.

S24What are the main known limitations?

The lidar sees one plane, so mapping is 2D; the tilted view raises walls visually, not from measured height. Supply voltage is not measured, so torque headroom at low charge is not compensated. The ToF layer covers only what the sensor has looked at. Self-uprighting is validated only from the front-bumper rest. Loop closure relies on scan matching against the existing map rather than a pose-graph optimiser. The safety bubble cannot see objects below the scan plane, glass or mirrors, and its braking parameters are model values to be confirmed by stopping tests.
